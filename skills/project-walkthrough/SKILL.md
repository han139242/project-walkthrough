# 项目开发复盘

站在准备向别人讲解项目的开发者视角，用一个真实使用场景把开发经历与当前实现串起来。听完应能说明当时为什么改、现在哪段代码负责、怎么知道它有效，以及哪些原因只有推测。

## 工作流程

1. **定位范围。** 用户点名的项目或功能优先。当前目录有唯一明确对象时直接开始，存在多个同样可能的对象且会导致整份讲义偏题时再确认。先用入口、项目说明和目录确认当前源码，识别是 Git 仓库、浅克隆、其他版本记录，还是独立文件夹。区分已部署、当前提交和本地修改。
2. **找发生过什么。** 按 [取证手册](references/evidence.md) 建立关键阶段。跟实际 diff、设计决定和验收记录走。没有 Git 就从带日期的文档、报告、备份差异和明确授权使用的消息里找观察点。只有当前源码时，讲可证的现状，将搭建顺序标为教学重构。
3. **解释每次取舍。** 给核心阶段写清「当时碰到什么 → 怎样定位 → 试过或参考什么 → 最后改在哪里 → 有什么验证」。原记录写明的理由直接锚定原文。由实现反推的工程理由说明推断依据。方案、结果、来源与动机缺证据时保留缺口。参考项目的相似性不能证明本项目曾借鉴。
4. **跟一条真实操作。** 从用户入口沿调用、数据转换、保存或执行、错误反馈追到终点。标出关键文件和函数。只有在两条链路能解释不同问题时才都展开。用一个真实故障或分歧把历史决策接到这条链路上，选必要的隔离验证或现有测试。
5. **交付可讲的版本。** 按 [讲义与复用](references/delivery.md) 写出时间线、决策故事、源码导读和可口述的短版本。先校对关键主张的定位、版本和验证边界，再检查读者能否循章节自己复述。用户请求简短讲解时在会话内直接给结果。用户说要直接念、复述或答辩时，单独给一段可以照读的口述稿。

项目默认只读取证。生成讲义是单独的交付，保留现有代码、记录和配置。沿用当前授权使用本地资料和工具。只有用户要求多模型或外部审阅时才交接，另行筛选允许分享的原文，检查旧日志、Git 历史和文档中的历史凭据及私人数据。可用时让外部模型独立复查关键分歧，再回原始证据裁决。
