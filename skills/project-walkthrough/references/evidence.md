# 取证手册

## 先对齐版本、对象和时间范围

- 记住要讲的对象、当前入口和实际检查到的版本。仓库可能套在工作区下面，一个工作区也可能有若干不同产品。Git 上层仓库存在时，确认它跟踪的确是目标文件。
- 按问题决定证据优先级。实现与变更用源码和 diff。原因、否决的替代方案和灵感来源用同期设计、提交正文、Issue 或明确授权查看的讨论。能否运行用相应版本的真实测试或验收。某个文件不存在只能说明这次查证范围内缺失。
- 只为可改变理解的阶段建索引。每条可简记为 `时间范围 | 项目/版本 | 主张 | 来源位置 | 能证明的范围 | 缺口`。关键主张附近给文件与函数、标题、完整或可唯一定位的 SHA、diff 或真实结果。目录列表和搜索匹配用于找位置，再打开原文。

## 有 Git

先确定 `HEAD`、当前工作树、历史范围与是否浅克隆。大项目可以从发布标签、第一父链和模块路径找候选，再挑真正改变正常路径或失败分支的提交。各分支里的开发先后和主线合入时刻分开解释。提交消息用于定位，重大转折至少核一次实际 diff。当前源码与提交不同则明确记为本地工作树行为。

```text
git rev-parse --show-toplevel
git rev-parse --is-shallow-repository
git --no-optional-locks status --short --branch
git log -n 40 --first-parent --format="%h %cI %s" HEAD
git log --name-status -M -- "<项目相对路径>"
git show --format=fuller --stat <commit>
git show --format=fuller <commit> -- "<项目相对路径>"
git diff -- "<项目相对路径>"
git diff --cached -- "<项目相对路径>"
```

提交前后路径或行为需要区分时，引用「SHA + 当时的文件路径」，讲现状再给今路径与函数。把模块内容没变与整个提交没改业务分开。路径重命名时，可对单个文件用 `git log --follow -- "<文件>"` 找旧路径，再校对 diff 或合并父提交。提交做了移除再加回、squash、浅克隆、导入快照或有本地未提交补丁时，避免无条件宣称「第一次」「最早版本」。需要 PR、远端分支或缺失历史才能改变关键结论时，说明权限与缺口，沿用已有授权获取。

某个模块的 Git 历史很复杂时，若已有获准使用的代码考古 Skill，可将目标提交索引或重命名线索当输入；最终选取与项目故事相关的证据并自行复核。

## 没有 Git，或 Git 太少

1. 用有明确日期或版本的设计稿、阶段交付、修复日志、测试结论、截图说明、带清单的版本包和授权记录定位阶段。文件名或修改时间只作检索线索，复制、解压和同步会改变它们。
2. 找「问题记载 → 具体改法 → 后续验证」的串联点。如有可信旧快照，核对单个文件或函数差异；只有旧方案与当前源码时，清楚写设计日期和现存实现。确定日期的故障、决定和验收仍保留在时间线上，其他依赖顺序单独注明是教学重构。
3. 后来的文字如果修正前一轮说法，保留当时观察和后续更正。例如早期有设备软件回执，现场复查发现缺实体动作证据。最终表述取证据能支持的范围。
4. 只有当前源码也可以教用户怎么搭。把顺序写成「根据当前依赖关系整理的实践顺序」，实际先后和个人贡献保持未知。

## 把动机与验证分开

| 要回答的事 | 允许怎样下结论 |
|---|---|
| 当时遇到的具体问题 | 引复现样本、日志、错误、用户反馈或对应测试。区分已出现和预先防范。 |
| 为什么选某做法 | 优先找同期明确理由、同条件对比或验收约束。只有 diff 时可解释该改法怎样解决问题，再标注设计动机是推断。 |
| 从哪里想到的 | 只有项目记录明确提到的参考才归为灵感来源。公开材料可以解释机制，不能替历史材料补动机。 |
| 哪些办法失败了 | 按实际执行、条件与结果描述。提议、放弃和实测未通过各有含义。 |
| 结果如何 | 写明时间、版本、样本与环境。真实 API 加合成输入、mock、真机回执、实物可见反馈和人工标签的证据不能互相替代。 |
| 谁做的 | 采用本人确认或可追溯分工记录。提交作者、提交者和操作 AI 的人可能不同。 |

如果复现会运行未授权服务、影响正式数据或产生费用，继续用源码、原始测试和低影响替代证据推进，把尚未复现的结论留在相应阶段。
