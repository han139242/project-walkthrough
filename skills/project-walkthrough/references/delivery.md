# 讲义与复用

## 让同一个项目能自己学，也能讲给别人

开头让读者能说出「谁在什么场景要完成什么」。按现存证据解释项目从什么底座开始，关键阶段为何改变，再跟踪当前真实路径。章节顺序可按依赖做教学调整，涉及真实年代时引用开发时间线。

适合较详细的交付结构：

- **项目怎么用。** 给具体输入和可见结果。列清核心模块对本场景负责什么。
- **怎么一步步搭出来。** 每阶段讲清已有基础、痛点、诊断、选法、关键文件、结果。选几次真正影响后面怎么做的变更，展开为什么成立和验证条件。
- **读源码。** 使用实际入口和文件/函数名跟一次正常请求，补一个拒绝、重试或回退。可以画短图，但节点和箭头要对应现有实现。帮助读者分清持久状态、临时状态与外部依赖。
- **可证的取舍。** 教读者如何用旧版本、diff 或已记录失败解释改动。用一两个易混证据示例推演错误结论，例如「消息收到」和「业务写入」，或「建议过」和「已部署」。
- **怎么讲给别人。** 给约 2 分钟的自然口述稿。较大的项目可附约 8 分钟的源码或演示顺序，再给两三道有对应检查位置的题。把当时的实测、这轮的测试和还缺的证据就近注明。口述稿按用户要讲的版本写，涉及工作树草稿或未核实的部署时，体现版本边界。
- **格式。** 默认用可搜索、带链接的 Markdown；用户要网页、Word 或别的形式时按要求。正文在能回查的地方给线索，不把所有提交细节塞进讲解。差异说明尽量带原文件位置，提交与工作树使用不同链接或标签。

## 交付前核对

从口述稿抽查三个容易夸大的说法，回到支持材料核对当时版本。用一条正常路径和一条失败路径读一遍代码。检查长篇讲义的本地链接。没有证据的位置收窄结论，无法改变结果的补查可以省略。

## 用户现在仍在开发，且希望以后留有理由时

在现有项目的决策记录、PR 描述或阶段验收中补一条即可。按用户给的授权写入，普通复盘直接读已有记录。优先记录本次要是丢了就无法从 diff 看出的判断。

```text
日期 / 变更或版本：
遇到什么，用什么输入复现：
试过什么，最后选什么，为什么：
参考来源与实际借用的机制：
改了哪些入口、文件或接口：
验证结果、环境与仍缺的证据：
```
